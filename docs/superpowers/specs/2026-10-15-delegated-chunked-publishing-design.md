# Delegated chunked publishing

## Scope and deployment

Create a standalone Move package outside `aptos-move/framework`, in `aptos-move/delegated-chunked-publishing/` with its own `Move.toml`, sources and tests. Deploy it independently to a caller-supplied address; the Aptos CLI's new stage/finalize commands require `--module-address`. Do not add it to the framework genesis bundle, alter `0x7::large_packages`, or change existing single-account chunked-publish commands. This package is a new interface, not an in-place upgrade of any existing deployment. All new entry functions and abort codes are documented in the module.

The package supports publication under an account, deployment of a new code object, and upgrade of a code object already owned by the publisher. The standalone contract uses the framework's existing `code::publish_package_txn` and `object_code_deployment::publish/upgrade` APIs; it changes no VM, cryptographic, consensus, or framework primitives.

## Accounts, authorization and state

A (stager) pays to upload a package; B (publisher) is the **only** signer permitted to finalize it. One staging area is stored under A. A starts it by naming B, then stages chunks under A's signature; later staging calls cannot switch B. A alone may clean up the staging area, even if upload or finalization is incomplete. B's final transaction supplies A's address; the module reads A's staging area, checks that its designated publisher equals B, and calls the framework publish function with B's signer. B's signature, not knowledge of a hash, authorizes publishing under B and ownership of a new code object. A cannot finalize a publish under B without B's signature.

Use a `TableWithLength<u64, vector<u8>>` with a key for each `(part, index)` and a list of keys for deletion. Part 0 is the BCS-serialized package metadata; parts 1.. are the ordered module bytes. Replaying an identical chunk is a no-op; sending different bytes to an occupied position aborts. Finalization takes explicit chunk counts (one positive count per part), refuses missing positions and extra staged keys, and assembles the bytes in part/index order. There is no append-only API in the new contract. Each new staging area carries a fresh generation ID; stage and cleanup calls must supply the same ID, so delayed transactions from an earlier upload cannot affect a replacement area. Cleanup removes at most ten table entries per transaction and the CLI repeats it, since deleting a very large area in one transaction may exceed on-chain write limits. Existing account-based staging elsewhere is unaffected. No new on-chain capability or authorization resource is needed beyond the designated B in A's staging area.

## Digest and publication

B must have an independent local copy of the package. Both CLIs compile with the **destination's** named addresses (B for an account publish, the intended code-object address for object publication), so the resulting module bytes and serialized metadata agree. Define the package digest as SHA3-256 of the BCS encoding of a pair `(metadata_serialized: vector<u8>, ordered_code: vector<vector<u8>>)`. The length-delimited BCS fields bind metadata, module count, order, lengths, and bytes; raw concatenation is not sufficient. Document the exact encoding and include cross-language known vectors so the Rust CLI and Move module agree. The CLI derives the digest from B's compiled package, never from A's on-chain data. Hashing uses the existing `std::hash::sha3_256`, not new signature or cryptographic code.

Before calling a framework publish function, the module checks B's designation, chunk counts and the digest of the assembled bytes against B's expected digest; any mismatch aborts. Transaction rollback preserves all of A's staged chunks on *any* failed finalization (including a framework rejection). B cannot consume A's staging area merely by knowing the hash unless A named B. B can decline to publish, leaving A free to clean up. On success, the staging area and its table entries are removed. The deletion refund is credited to the final transaction's gas payer, normally B, **not** automatically to A, who paid the initial storage deposits. With a separate sponsored fee payer, that payer receives the refund; this is an explicit economic trade-off, not a reimbursement scheme.

## CLI contract and transaction modes

Add dedicated `aptos move` subcommands for (1) A to stage a local package with B's address and (2) B to finalize a package staged by A with B's local package and a destination (account, new object, or existing code object). Both require `--module-address`; the finalization command requires `--stager` and validates the contract's module ABI. A's command creates the staging area in an initial, committed transaction before it sends chunk transactions. A resume reads the staging area at A's address, verifies it names B, checks staged positions and bytes against the local compilation at one ledger snapshot, reuses that area's generation ID, and submits only missing chunks. The CLI checks the expected function names and address but does not establish the trustworthiness of arbitrary deployed bytecode; A and B must independently verify the deployment at `--module-address`. A must explicitly clean up data for a different package; never silently consume or overwrite it.

For staging on a chain with the orderless feature enabled, default to nonce replay protection and send a bounded group of position-keyed chunk transactions concurrently. Read the on-chain orderless feature flag from the REST API; a failed feature lookup fails explicitly rather than guessing support. Expose an override to force nonce or sequence-number mode: forcing nonce on an unsupported chain produces a clear error. In sequence-number mode use consecutive account sequence numbers, still include positions so restart/resume stays idempotent, and preserve bounded parallel submission where safe. Neither mode depends on the arrival order of chunk transactions. Wait for every staging transaction to commit before reporting success or suggesting finalization; report failures and preserve successfully staged chunks for resumption. For `--session` or other offline simulation modes, use sequence numbers and the existing in-order submitter unless nonce support can be verified in that environment.

Finalization is a separate B-signed transaction. For a new object, A's stage command requires B's **expected object-seed sequence number**, defined as B's on-chain sequence number plus one, and derives the destination code-object address from it before compiling the modules; B's finalize command checks that same value and independently compiles for that address. The final transaction uses B's actual current sequence number (`expected object-seed sequence number - 1`), because `object_code_deployment::publish` builds its seed from `account::get_sequence_number(B) + 1`. This is not an on-chain reservation: B must avoid other sequence-numbered transactions until finalization. If B's sequence changes, either the CLI preflight or the chain rejects the final transaction; A's staging remains untouched. Staging under A (nonce or sequence transactions) never changes B's sequence number. For upgrades, apply the framework's existing code-object ownership checks. If an object-address/named-address mismatch is detected at compilation or before finalization, fail rather than publish the wrong bytes. Legacy `0x7` and immutable mainnet `large_packages` do not expose this interface; the new commands give an unsupported-module error instead of trying their append functions.

## Testing, errors and limits

Move unit tests: unauthorized B or A, wrong digest, wrong counts, missing or extra positions, conflicting versus repeated identical chunks, protected cleanup, and success/abort preservation. Unit tests check that B's signer is passed to the framework, and e2e tests confirm an account package is published under B, a new code object belongs to B, and upgrades still enforce code-object ownership. Digest known vectors test that Rust `bcs::to_bytes(&(metadata, code))` matches the bytes produced by Move BCS serialization of a private two-field preimage struct; the Move language cannot directly serialize a tuple. Failures return named abort codes and leave staged data intact. Validate the full-package hashing gas cost on a large package before declaring it safe for mainnet gas limits.

Run a fresh `aptos node run-localnet` using a node/CLI built from the stacked branch, deploy the standalone module at an explicit address, fund distinct A and B, upload from A using orderless nonces, and finalize from B using an independently compiled local package. Check the on-chain publisher and code, staged-resource removal, transaction outcomes, and the fee statement's storage refund. Force a sequence-number staging run, interrupt it, resume the missing positions, and publish. Before successful finalization, attempt a mismatched local package digest, an unauthorized publisher, and incomplete staging; verify each fails and A's chunks remain. Exercise new-object publish with B's expected sequence-number-derived address, including an intervening B transaction that changes the sequence number (finalization must fail without consuming A's staging), and an owner-authorized upgrade. Verify unsupported ABI and unsupported orderless-feature errors. Existing single-account `large_packages` behavior remains covered by its prior tests; this work does not rebuild its framework bundle because no framework Move source changes.

Never infer that possessing the hash authorizes B, infer successful publication merely from submitting transactions, or hide an ambiguous replay-protection/feature-check failure by silently changing modes. Public testnet and a multi-validator swarm are not included; the supported deployment is the separately published module on a fresh CLI localnet, followed by review before use on a production network.
